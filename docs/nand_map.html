F700 NAND map

What an Alcor F700 USB stick holds on its flash chip after a low-level format (LLF). A dashed outline marks what the controller reads at power-on (section 4).

1. The big picture

Host

Sees only a plain disk (about 16.6 GB, capacity from the 99 record). It never sees blocks, pages or the reserved area below.

Controller

USB 058F:6387, chip ID F700 (family CTL-28). The firmware (FTL, flash translation layer) decides where each sector lives and keeps its own tables in a few reserved blocks. It is configured with vendor FA 0B commands; see commands.md.

The FTL splits the die into 4 lanes (block mod 4, 548 blocks each), 8 units × 4 cell slices, with a superblock stride of 0xF4 blocks.

NAND chip

Micron 32-layer 3D MLC, 128 Gbit, 1 CE (AlcorMP's label MT29F128G08CBCDB). No public datasheet; the numbers come from AlcorMP's FlashList record and the chip's ONFI page.

2. The block map

Block addresses 0x000 to 0x88F, drawn not to scale so small regions stay clickable.

FTL system, block 0x000

The primary copy of the controller's bookkeeping: 256 pseudo-SLC pages, not to scale. Click a page. Block 0x0B2 holds the same records one page lower (the FTL mirror). The records chain: the anchor points to the frame record (page 0x0F), the frame record to the configuration record, the configuration record to the ECC table.

Page 0x00: FTL anchor

The mask ROM reads it first at power-on (mirror: block 0x0B2 page 0x88); unreadable, the controller stays in ROM mode (058f:1234).

0D 06 05 06 38 record, 0x80 B tiled. Byte 0x2E (0xDA) is a geometry-derived NAND attribute, not a write-protect flag (nand.md).

Page 0x01: lane bitmaps

Four bitmaps of 0x200 B, one per lane (bit i = lane block L+4i marked), plus the LLF pattern.

Input of the firmware's free-block allocator, which also places the info record page: a bad block left unmarked here can be handed out.

Pages 0x02-0x0C: boot firmware

36_L04A_CB.BIN, one 4 KB block per page, then that page's pattern slice. The first two blocks carry the FTL self-descriptor: system block, data superblock, spare blocks, page list. The spare-block choice varies per run.

At power-on page 0x02 (firmware page 0) is mapped at CODE 0xC000; overlay n (page 0x03+n) is loaded into 0xD000 whenever the firmware needs it, so these pages are read for as long as the stick runs.

Page 0x0D: ECC parameters

BCH parameter table, ecc_params.tsv record 00 04 02 4e.

Page 0x0E: FTL configuration ×2

Firmware-page pointers, lane, options and the FA 13 trim byte.

Page 0x0F: frame record ×2

8 frames of 0x28a bytes plus a pointer to page 0x0E.

Pages 0x10-0xFF: system pages

LLF pattern pages (complement of page · 0x1000).

Reading back: raw reads (alcortool dev nand read) return pages 0x00-0x03 and 0x0D plain; pages 0x04-0x0C (overlays 1-9) are stored scrambled by the controller's write randomizer (seed unknown), so a raw block-0 read is not a firmware backup.

FTL translation, blocks 0x001-0x003

ae translation tables, 256 pages each, computed by the controller (the host sends only the headers).

Bad-block screen & scratch

Each block in 0x000-0x08F is test-written (page 1) and erased. A block whose read-back fails (red: an example die) gets a retention march from AlcorMP (pages 1, 2, 4 … 256) and is marked screen-bad by the tool. Scratch block 0x058 takes a 32-page pattern, verified then erased. Boundary-scan bases (0x04C 0x04E 0x06D 0x06F) are erased ECC-margin targets.

FTL mirror, block 0x0B2

Block 0's records one page lower, with the anchor at page 0x88 instead of page 0. The anchor's self/mirror pointers differ between the copies.

FTL units, 0x0F4-0x0F7 + n·0xF4

32 blocks that the format only reads back (logical → physical map), using commands 91 92 9a 99.

Data blocks & superblocks

Initial data blocks are 0x100 + 4i + lane (45 on lane 0, 40 on lanes 1-3), listed by the superblock head pages and marked in the lane bitmaps.

Two data superblocks, in the lanes of 0x000 and 0x0B2: 4 header pages + 252 pattern pages each. AlcorMP picks different ones per run (e.g. 0x2EC/0x1EA).

Housekeeping, block 0x400

25 encoded FTL table pages: header, page list, system record, slot map, per-block status, lane records, MP info. AES-256-CBC + Reed-Solomon (ftlcrypt.py). AlcorMP's bad-block table store.

Page 0: header

A 0x100-B struct, stored 4 times: the page of the page list (0xA2) and of the system record (0xC8), the chip ID (0xB0, F700), the block span (0xE0), the lane-record size (0xED, 0xFE) and the format date (0xFA: year, month, day). The other bytes are MP state and F700 constants (?).

Page 1: page list

One little-endian word per page: table type | page number, FF after the last.

Page 2: system record

AA at 0, AlcorMP's INI name at 0x02-0x21, the planned capacity (sectors, little-endian) at 0x27, 80 at 0x2B.

Page 3: slot map

0x100 little-endian entries, entry i = i, then FF.

Pages 4-7: block status

AlcorMP's bad-block table: one byte per block over the 0x1000 block-address span. A block's worst c0/c1 read-back value (bit errors); above 0x9F it is bad; 0xE0 ORed in when a 05 report or the screen flagged it; FF past the die (0x890 up). Without the sweeps: 0, and 0xE0 for screen-bad blocks. alcortool format --bad-blocks keep reuses it; alcortool dev housekeeping lists it.

Pages 8-23: lane records

4 KB (4 pages) per FTL lane: the lane number (0x12, 0x29), its blocks (0x18: 548), pages per block (0x24), sectors per page (0x26), the lane count (0x28), the capacity in MiB (0x2A) and its good blocks (0x30: the lane's blocks less the bad ones). The rest are F700 constants.

Page 24: MP info

0x100 B stored 4 times: a fixed head (aa 01 00 00 00 05 04 19 01), the host name at 0x40 and the user name at 0x60 of the machine that ran the format (the tool writes alcortool).

Info record page

The first thing the mount reads after the firmware is loaded. It is a whole block taken from the free list (the initial data blocks a data-superblock head page lists), tagged 07FC in the page-0 spare, and moved to a fresh block on every update. At power-on the firmware finds it by that tag.

Sector 0: the info record

Vendor opcode 96 serializes the record from RAM and saves it as sector 0; a format without it leaves sector 0 erased, which gives capacity 0xFFFFFFFF, WP on and a locked firmware (058f:9380) at the next power-on.

Policy WP is switched without a format: 9B sets it in RAM, 96 saves it here (alcortool unlock, --lock).

Sector 1: the config block

The 99 07 block: USB VID:PID and descriptor, the USB and SCSI strings, the serial; the ROM checks it. Written by 81 00 FF; full table in structures.md.

Sector 2: lock block

Blank (FFFF at 0x80) after a format. Set, the LUN is write-protected (option bit 70) and the 99 record is refused. The partition-password record (?); nothing in AlcorMP's or the tool's format writes it.; meaning

Sector 3: lock block

Blank after a format. Set, the area up to the record's F5 bound is refused. The secure-area record (?).; meaning

Sector 4: MP info

Written by the format (81 51 04): AlcorMP's constant state block, the format date and capacity, 55 AA.

Sectors 5-7

Blank (FF) after a format. The mount reads sector 7 with sectors 1-3, for a purpose not known.

User data

Everything else: whatever the host writes after the format.

3. Inside one page

Data area

16384 B per page, 512 pages per block (256 on the FTL system blocks, which run pseudo-SLC).

Spare area & ECC

BCH over 1 KB codewords, 16 frames per raw page. t = 0x4E (78, frame 1162 B) fills the raw page; t = 0x48 (72, frame 1152 B) leaves 160 B. The stick's own NAND set-up says t = 78.

4. Power-on: what the controller reads

  1. Mask ROM starts and reads block 0x000 page 0x00 (anchor). Nothing readable: stays in ROM mode, 058f:1234, where a full format runs.
  2. Reads block 0 pages 0x02-0x03 in SLC mode: firmware page 0 and overlay 0 into the overlay window, and jumps in; overlays 1-9 (pages 0x04-0x0C) load on demand.
  3. Mount: from the lane bitmaps (page 0x01) and the free-block list the firmware finds the info record page and reads it: capacity, options, WP, lock gate, then the config block in sector 1. No record: defaults (capacity from the lane counts). Erased record: locked, 058f:9380.
  4. Picks the first lane with usable blocks and enumerates on USB with the config block's VID:PID.

The boot, mount and lock gate: processes.md; addresses: F700.md.
